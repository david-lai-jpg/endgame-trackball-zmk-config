# Personal Marshmellow UI Notes

Settings live in the trackball's own memory, not in this repo. Flashing firmware keeps them (the firmware ends before the settings area at 0x6c000), but a settings reset loses them; send the commands below in the Marshmellow UI terminal to restore.

## Pointer

No acceleration curve, by choice (David, 2026-11-07): the cursor moves at a fixed 25% sensitivity. Do not load a pointer curve.

## Scroll (2026-11-07)

Used mostly on macOS (with SteerMouse wheel mode "Linear" for the Endgame), sometimes on Windows. Default OS mode is macOS: `bistable set 1`, `rtcfg set bst/default 1`. Switch the trackball to Windows mode (slot 0) on Windows: hold the Device-layer button (pos 7) and press pos 4 (OS toggle, flashes cyan), or `bistable set 0`. The chosen mode is saved and survives restarts.

- macOS mode (2026-11-11): drag `rtcfg set bst/dragscroll/s1_mult 2`, `rtcfg set bst/dragscroll/s1_div 1` (2.0x, both directions); twist `rtcfg set bst/twist/s1_mult 33`, `rtcfg set bst/twist/s1_div 20` (1.65x; 2.0 was too fast, 1.6 too slow). These gains sit before the curve and go with SteerMouse "Linear" on Roll Up / Roll Down and on Roll Left / Roll Right (see "SteerMouse left-right scroll" below; the Tilt Interval of 1 ms used from 2026-11-11 to 2026-11-14 was wrong); before that day both were 1/1 and macOS acceleration made up the difference on the cable.
- Windows mode: `rtcfg set bst/twist/s0_div 3`, `rtcfg set bst/dragscroll/s0_div 3` (Windows scrolls 3 lines per unit, macOS 1)
- `curve set scroll 0 0 100 9 10 9 10 9 100 9 6000 40 2000 9 4000 40` (twist: 0.09x up to step ~8, smooth rise to 0.40x at step 60)
- `curve set dragscroll 0 0 100 6 10 6 10 6 100 6 6000 21 2000 6 4000 21` (drag: 0.06x, smooth rise to 0.21x at step 60)
- Left-right drag boost: `rtcfg set bst/dragscroll_x/s1_mult <n>`, `rtcfg set bst/dragscroll_x/s1_div 10` (`s0_*` for Windows mode; 10/10 = off, which is the value in use and the default of the main build from 8d387fd on). Trap (logged 2026-11-14, user chose not to flash): the build on the trackball is 0f43113, whose default is 20/10 = 2.0x; only the saved 10/10 keeps the boost off. After a settings reset, send `rtcfg set bst/dragscroll_x/s1_mult 10` and `rtcfg set bst/dragscroll_x/s0_mult 10`, or flash the current main build. Corrected 2026-11-11: the boost was added on a wrong diagnosis. The trackball sends as much left-right (HID pan) as up-down (HID wheel) for the same stroke. The cause of slow, short, jerky left-right drag scroll was SteerMouse: its Wheel tab handles left-right as "Tilt Left" / "Tilt Right" = Scroll, Linear, 1 line, repeat Interval 50 ms, so it replaced the trackball's pan with one 10-point step every 50 to 60 ms at any hand speed. The fix of that day (Interval 1 ms on Tilt Left and Tilt Right) was replaced on 2026-11-14; see "SteerMouse left-right scroll" below. Not the cause, each tested: twist detection, the axis clamper (never locks with `ac/history_ttl` 0), sensor or hand gain.
- `p2sm sens twist set 150` (15%)
- Twist detection: `rtcfg set p2sm/twist_dy_mag_mul 3`, `rtcfg set p2sm/twist_dy_mag_div 2` (start needs twist > 1.5x roll, default 2x), `rtcfg set p2sm/twist_act_ms 8` (default 25), `rtcfg set p2sm/twist_deb 15` (default 35), `rtcfg set p2sm/twist_hyst_mul 1` + `rtcfg set p2sm/twist_hyst_div 1` (continuation needs twist > roll, default 7/6), `rtcfg set p2sm/twist_ttl 120` (default 65). Tighten these first if twist scroll starts by accident.

Why the curves look like this: the curve's speed input is the per-event scroll step after the OS-slot divider. With divider 10 that step was a whole number of 1 to 5, so any speed-up curve jumped (the "Aggressive" preset went from 0.29x at step 1 to 1.06x at step 4, about 14 times the output for a little more force). With divider 1 the step runs from 1 (slow) to about 110 (hardest twist), measured with `curve monitor on --abs`, and the curve does the dividing with y below 1.0, so the speed-up is smooth. Set the slow speed with the curve's base y and the flick distance with its end y. The Windows divider sits before the curve, so on Windows the speed-up starts at 3 times the speed and flicks go about half as far as on macOS (accepted, 2026-11-07).

## Firmware scroll settings (2026-11-07)

- `CONFIG_ZMK_POINTING_SMOOTH_SCROLLING=n` in `config/efogtech_trackball_0.conf`. Measured with a macOS scroll-event tap: while the HID Resolution Multiplier is declared, macOS turns every wheel report into one 1-line step whatever its value, so fast scrolls and flicks were capped. Without it macOS keeps the value (events up to 36 lines seen). On macOS 1 unit = 1 line = 10 px. Cost: Windows loses sub-notch (high-resolution) scrolling; 1 unit = 1 notch there.
- `sync-scroll-report-ms` stays `<8>` in `boards/arm/efogtech_trackball_0/pointer.dtsi`. A 4 ms build (2026-11-07) made cursor, drag and twist feel floaty and jumpy; the user kept the 8 ms build.
- `twist-interference-thres = <0>` in the same file. The default 200 drops a twist step whose roll part is over 200 counts. It was not the cause of dropped fast twists (the HID multiplier was); it stays because the relative twist-vs-roll check still guards.
- With SteerMouse off, macOS's own scroll acceleration stacks on the curves and small twists jump; keep SteerMouse "Linear" for the Endgame.
- SteerMouse keeps one device entry per connection type (USB or Bluetooth), and it does not tell ZMK devices apart by name: all of them report vendor 0x1D50, product 0x615E. Seen 2026-11-09: the Endgame on Bluetooth ran under an old "Eyelash Corne" Bluetooth entry (green), and the "Endgame" entry (USB: cable or dongle) stayed grey. So the Endgame needs its "Linear" settings in the entry that turns green on each connection type.
- Measured 2026-11-11 on the USB cable: the Endgame's USB identity is vendor 0x0011, product 0x0006 (SteerMouse key `11-6-0-USB`); 0x1D50/0x615E is its Bluetooth identity, and the Bluetooth link can stay connected while output is USB. On that cable entry, up-down scroll had no SteerMouse events and got macOS acceleration (about 100 points per wheel step); set Roll Up / Roll Down to Scroll, Linear there too. To see what SteerMouse does, log `eventSourceUnixProcessID` in a listen-only CGEvent scroll tap: SteerMouse-made events carry its process ID, device events carry 0.

## SteerMouse left-right scroll (2026-11-14)

- Problem: left-right drag scroll went much too far at slow speed and jumped, worst when panning a board in Brilliant. Cause: SteerMouse reads the Endgame's left-right scroll (HID pan) as a tilt switch, not as a rolling wheel. With Tilt Left / Tilt Right = Scroll it drops the trackball's own left-right events and sends its own 10-point steps on a timer for about 235 ms after each pan report (about 80 steps per second at Interval 1 ms; measured: a flick with 20316 points going in gave 260 points to the app, a slow pan ran at about 800 points per second). With No Action it blocks left-right scroll. No Interval value makes this follow the ball.
- Fix, SteerMouse only, no firmware change: a user device definition that marks left-right as a rolling wheel. File: `/Users/david/Library/Application Support/SteerMouse & CursorSense/Device Definitions/Endgame Trackball.xml`, a plist with `personalities` (vid 0x0011 / pid 0x0006 for the cable, vid 0x1D50 / pid 0x615E for Bluetooth) and `hScrollOp` = `Roll`. The key and its values (`None`, `Tilt`, `Roll`) come from SteerMouse's own files in `/Applications/SteerMouse.app/Contents/Resources/Device Definitions/` (SteerMouse 5.8.2; `Roll` is used for the MX Master thumb wheel and the Kensington Expert TB800). The Bluetooth ID is shared by every ZMK Bluetooth device, so the file also applies to the Corne Min.
- To load the file: quit SteerMouse, run `launchctl kickstart -k gui/$(id -u)/jp.plentycom.boa.SteerMouse` (the background helper reads definitions at start), open SteerMouse again. The Wheel tab then shows Roll Left / Roll Right in place of the Tilt rows; set both to Scroll, Linear, like Roll Up / Roll Down, in each entry (cable and Bluetooth).
- Result on the cable (measured 2026-11-14, user: "worked perfectly"): the app gets only the trackball's events, each one a 10-point step, in both directions; per unit of ball input 0.62 points left-right and 0.64 up-down. Bluetooth (same day, after the Bluetooth ID was added and Roll Left / Roll Right were set in the "Endgame BT" entry): left-right 178 and up-down 186 trackball events, each a 10-point step, none made by SteerMouse; user: "works perfectly now". Full test status: `steermouse/steermouse-setup.md`.
- Measured the same day: with Linear, SteerMouse turns every scroll report into one step of exactly 10 points, whatever the report's value. So what the app gets follows the number of reports (at most one per 8 ms), not their size. The scroll curves and gains change the feel only through how often a report is not zero.
- Trap for measuring: a CGEvent tap placed with head insert sees scroll events before SteerMouse changes or drops them. To see what apps receive, add a tap with tail append (session or annotated session) and compare. Measurements before 2026-11-14 used a head tap only, so their point and line values are the values going into SteerMouse.
- To check or restore this setup: `steermouse/steermouse-setup.md` in this repository, with a copy of the file in `steermouse/Endgame Trackball.xml`. The live file and the SteerMouse entries exist only on the Mac. A copy of the settings store from before the change is next to the store: `Device.smsetting.backup-20261114-1307`.
